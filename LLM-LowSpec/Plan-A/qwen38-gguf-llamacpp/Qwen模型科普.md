# Qwen 模型命名后缀科普

> 以你在本地部署的模型为例：`Qwen3.8-27B-FP8`、`Qwen3.6-35B-A3B-FP8`。
> 拆开看，它们由 `系列名 + 参数量 + 结构 + 量化格式` 组成。

---

## 一、后缀里的数字代表什么：`B` / `27B` / `A3B`

**`B` = Billion，单位"十亿"，表示模型参数总量。**

- `27B` = 模型共有约 **270 亿个参数**。
- `35B` = 约 **350 亿个参数**。

参数越多，模型"记的东西"越多、通常越聪明，但也越占内存、越慢。
直接落地到你的机器：1 个参数存 2 字节（bf16）约 2GB/10 亿参数；存 1 字节（fp8）约 1GB/10 亿参数。

**`A3B` 里的 `A` = Active，表示"每生成一个 token 实际激活的参数"。**
这种写法专属于 **MoE（专家混合）模型**：

- `Qwen3.6-35B-A3B` = 总共 **35B** 参数，但每次只激活约 **3B**。
- `Qwen3-235B-A22B` = 总 235B，激活 22B。
- 有的写 `30B-A3B`、`MoE-A2.7B`，含义相同：`总参数B-激活参数A xB`。

**为什么"总参数大"却很省算力？** 因为省下的不是"存储"，而是"计算"——下个 token 只算那 3B 激活参数，GPU 忙的时间大幅减少，这就是它比同总参数的稠密模型快的原因。

---

## 二、稠密 vs MoE vs 专家模型

一个模型就是一堆"层"（layer）。关键区别在"每个 token 要不要算完所有层里的所有参数"。

### 稠密模型（Dense）
- **每个 token 都必须算一遍全部参数**，一个不落。
- 例：`Qwen3.8-27B`（本地这个）、`Qwen3-32B`、Llama-70B。
- 特点：实现简单、容量 = 单个巨大网络，但**计算量 = 总参数量，随着参数变大线性变慢**。
- 本地表现：27B 稠密，AirLLM 每生成 1 个标点都要逐层读完全部 64 层，所以 ~0.025 tok/s 已是天花板。

### MoE（Mixture of Experts，专家混合）模型
- 把网络中"前馈层"拆成**很多个专家（expert）网络**，外加一个**路由器（router）**。
- 每个 token 由路由器挑出**最合适的 top-k 个专家**来算（通常 k=8/16），**其余专家跳过**。
- 例：`Qwen3.6-35B-A3B`、Mixtral-8x7B（8 个专家）、Kimi K3（每层 896 个专家、路由 16 个）。
- 特点：**总参数可以很大（容量大、记得多），但每次只激活一小撮专家（算得快）**。
- 代价：专家参数再多，存储/磁盘也还是要全放；内存、磁盘占用按总参数算。

### 专家模型（Expert）
- 就是指 MoE 内部那些"专家子网络"本身，或者是"用 MoE 结构"的口语说法。
- "专家"不是独立模型，而是**大模型内部的一组可切换的小网络**。
- 在 AirLLM 里，对 MoE 有专门的"按专家流式"：只把 token 命中的那几个专家加载到 GPU，其余留在磁盘。

### 一句话对比
| | 稠密 | MoE |
|---|---|---|
| 每次算的参数 | 全部（=总参） | 只有激活的一撮 |
| 记忆容量 | 按总参 | 按总参（可很大） |
| 计算速度 | 总参越大越慢 | 看激活参（可快） |
| 存储/内存 | 都要全放 | 也要全放 |
| 例子 | Qwen3.8-27B | Qwen3.6-35B-A3B |

## 三、量化（Quantization）是什么

量化 = **降低参数的数字精度，用更少字节存同一个权重**，从而省内存、省传输、变快。

### 精度档位（每参数占多少字节）
| 表示 | 含义 | 字节/参数 | 精度 |
|---|---|---|---|
| fp32 | 32 位浮点 | 4B | 最高（不常用，太大）|
| fp16 / bf16 | 16 位浮点（训练常用）| 2B | 高，近乎无损 |
| fp8 | 8 位浮点（e4m3）| 1B | 中高，本地 `-FP8` |
| int8 | 8 位整数 | 1B | 中 |
| NF4 / int4（4bit）| 4 位 | 0.5B | 中低，需配合量级缩放 |
| GGUF Q4_K / Q5_K / Q8_0 | llama.cpp 的 4/5/8-bit 变体 | 0.5~1B | 各档，主流推理常用 |

### 量化为什么能"变快又更省"
- **内存/显存减半到减 8 倍**：27B 模型 fp8 只有 ~27GB，bf16 要 ~54GB。
- **磁盘读量变少**：流式/低内存部署时，读进来的字节数大减（这正是你方案4 NF4 提速的本质——把读量再压低 4 倍）。

### 量化的代价
- **精度损失**：压缩后数值有误差，输出质量轻微下降，量化越狠损失越大。
- fp8 在企业里常被认为"近似无损"；4bit 对敏感任务偶有可感知偏差。
- 位宽与质量的关系不是线性的，8bit 通常很安全，4bit 需要好的方法（NF4、GPTQ、AWQ）。

### 两种量化思路
- **校准式（离线）**：GPTQ、AWQ——用一批数据计算最优缩放/量化，精度更稳，但需要校准步骤。
- **动态/直接式**：NF4（bitsandbytes）——按块算缩放，无需校准，部署简单（你方案4 用的就是它）。

### KV Cache 量化
- 除了权重，生成时的"注意力缓存（KV）"也占显存，也可量化（如 fp8/int8 KV），用来省显存、撑更长上下文。

## 四、把后缀连起来读

| 模型名 | 拆解 | 含义 |
|---|---|---|
| `Qwen3.8-27B` | Qwen3.8 系列 + 27B 参数 | 27B 稠密基准版 |
| `Qwen3.8-27B-FP8` | 上面的 + FP8 量化 | 27B 稠密、权重用 8 位浮点存储 |
| `Qwen3.6-35B-A3B` | 35B 总参 + A3B 激活 | MoE，总 35B，每次激活 ~3B |
| `Qwen3.6-35B-A3B-FP8` | 上面的 + FP8 | MoE 35B/激活3B，fp8 存储 |
| `Qwen3-235B-A22B` | 235B 总 + A22B 激活 | 超大 MoE，激活 22B |
| `Qwen3-32B`、`Qwen2.5-72B` | 无 A | 稠密模型（无 MoE），直接标总参 |

## 五、对照你的部署现状

- **`Qwen3.8-27B-FP8`（阶段A，正在优化）**：27B **稠密**，fp8 存储。
  因为是稠密，每生成 1 个 token 都要算完 64 层全部参数 → 在 8G/16G 上天然极慢（~0.025 tok/s 已是优化后）。
- **`Qwen3.6-35B-A3B-FP8`（阶段B）**：35B **MoE**、激活仅 3B → 每 token 算力远小于稠密，理论上会快很多。
  但它是 fp8 存储 34.9GB，加载/分片阶段在 16GB RAM 上就 OOM（内存不够，还到不了"靠激活省算力"那一步）。
- **方向**：要"变快"应转向 **小体积 MoE + 更强量化（如 4bit）以把总存储压进内存**，让"只算激活 3B"的优势真正落地；在稠密 27B 的 AirLLM 路径上只能优化系数、不能质变。

---

*附：常用术语速查*
- **token**：模型读写的基本单位，中文大致一个字词。
- **tok/s**：每秒生成的 token 数，衡量推理快慢。
- **prefill**：先"读完"输入的那一遍。
- **KV cache**：生成时缓存历史注意力，避免重复计算。
- **路由器 / 激活专家**：MoE 里选择"谁上场"的机制和被选中的专家。

# 附录：大模型后缀最全清单

一个完整命名通常按这个顺序叠：`系列 - 参数/结构 - 用途/变体 - 审查/合并 - 量化 - 格式`

```
Qwen3.6 - 35B-A3B  - Uncensored-HauhauCS-Aggressive  - IQ3_M  .gguf
└─系列   └─尺寸/结构    └─审查与合并配方          └─量化    └─格式
```

## 六、参数量 / 尺寸后缀

| 后缀 | 含义 | 例 |
|---|---|---|
| `B` | Billion，十亿参数（大模型通用）| 7B、27B、70B、235B |
| `M` | Million，百万参数（仅超小模型）| 0.5B、1.5B |
| `A x B` | Active，每次激活的参数（MoE 才用）| `-A3B`、`-A22B` |
| `-Mini / -Nano` | 精简小号（同代里的轻量版）| `Qwen2.5-0.5B`、`-Mini` |
| `-Max / -Plus / -Turbo` | API 的大号/进阶/极速档 | `Qwen-Max`、`Qwen-Plus` |
| `-lite` | 轻量变体 | 常出现在替换/API 名 |

> 注意：`Mini/Max/Plus` 很多是 **API 档位名**，不一定有对应开源权重。

## 八、审查、风格与合并配方后缀

这部分社区魔改命名最杂，主要来自 HuggingFace 的 merge/RP/NSFW 生态。

### 审查去除（去掉拒答）
| 后缀 | 含义 |
|---|---|
| `-Uncensored` / `-NonCensored` | 去掉安全拒答，能聊审慎内容 |
| `-Abliterated` / `-abl` | "去审查手术（abliteration）"的处理版 |
| `-NSFW` / `-Ero` / `-Spicy` | 内容尺度标签（成人向）|
| `-Aggressive` / `-Strong` / `-Harsh` / `-Gentle` / `-Soft` / `-Medium` | 去审查或角色塑造的**强度**层叠 |

### 合并配方 / 作者名
| 后缀 | 含义 |
|---|---|
| `HauhauCS` | 社区**合并作者/配方名**（这类名可任意，是一条生意的标识）|
| `-Slerp` | 球面线性插值合并（一种权重融合算法）|
| `-DARE` / `-TIES` / `-Frankenmerge` | 其他权重合并算法/手法 |
| `-Merge` | 泛指用多模型合出来的模型 |
| `-Dev` / `-Creative` / `-Glory` | 面向开发者/创造力风格微调 |
| `-RP` | Roleplay 角色扮演微调 |
| `-Story` / `-Narrative` | 叙事/故事生成微调 |

> 合一枚：`Qwen3.6-35B-A3B-Uncensored-HauhauCS-Aggressive-IQ3_M` =
> 35B MoE 基础款 + 去审查 + 某作者合并配方 + 激进风格层 + IQ3_M 量化。

## 九、量化后缀（最乱、最该会看的部分）

量化会同时写"**方法 + 位宽 + 精度档**"。分几大流派：

### 1. GGUF 家族（llama.cpp，社区标配，`.gguf` 文件）
`Q`=量化，数字=位宽，`_S/M/L`=档位，`K`=K-quant（带重要性加权的混合量化）。

| 常见档位 | 说明 | 大致大小(7B) |
|---|---|---|
| `Q2_K / Q3_K_S / Q3_K_M / Q3_K_L` | 低比特 K-quant | ~2.6~4GB |
| `Q4_K_S / Q4_K_M` | 4bit 甜点档，**社区最推荐** | ~4.4GB |
| `Q5_K_S / Q5_K_M` | 5bit 高保真 | ~5GB |
| `Q6_K` | 6bit | ~5.7GB |
| `Q8_0` | 8bit，几乎无损 | ~7.4GB |
| `Q4_0 / Q4_1 / Q5_0 / Q5_1` | 老式、无 K 的逐块量化 | 略逊于同档 K |

### 2. IQ 家族（GGUF 的"重要性矩阵"量化，需 imatrix 才最佳）
`IQ` = Importance-matrix Quantization，用校准统计让低比特更准，档位更细。

- `IQ1_S / IQ1_M`（极低比特）
- `IQ2_XXS / IQ2_XS / IQ2_S / IQ2_M / IQ2_XXL`
- `IQ3_XXS / IQ3_XS / IQ3_S / IQ3_M / IQ3_L`
- `IQ4_NL / IQ4_XS / IQ4_XXS`
- `IQ8_M`

> `IQ3_M` 就是"3 位重要性矩阵量化·中档"。IQ 通常在同位宽下比老 Q 更准，但**没跑 imatrix 可能反而略差**，老手普遍推荐 K 档起步。

### 3. bitsandbytes 家族（HuggingFace 直接加载）
| 后缀 | 含义 |
|---|---|
| `-NF4` | NormalFloat4，4bit 块级动态量化，部署简单（你方案4 用的就是它）|
| `-FP4` | 4bit 浮点 |
| `-Int8` | 8bit 整数 |

### 4. GPTQ / AWQ（校准式低比特，GPU 原生跑）
| 后缀 | 含义 |
|---|---|
| `-GPTQ` / `-GPTQ-Int4` | 需要校准集的 4bit 量化 |
| `-AWQ` / `-AWQ-Int4` | activation-aware 校准量化，通常比 GPTQ 更稳 |

### 5. EXL2（ExLlama 生态的按位宽量化）
- 后缀用 `-bpw`（bits-per-weight，每权重位数），可带小数：`-2.5bpw / -3bpw / -4bpw / -4.25bpw / -5bpw / -6.5bpw / -8bpw`。
- 数字越大越接近原模型；约 6.5bpw+ 接近无感。

### 6. 平台/容器专属
| 后缀 | 含义 |
|---|---|
| `-MLX` | Apple 统一内存（M 系芯片）版 |
| `-ONNX` | ONNX 开放神经网络交换格式 |
| `-FP8` / `-BF16` / `-F16` | 原始高精度权重（你的 `-FP8` 就在这档）|

## 十、容器 / 文件格式后缀

| 后缀 | 含义 |
|---|---|
| `.gguf` | llama.cpp 的**统一量化容器文件**，把量化权重打包成一体文件 |
| `.safetensors` | HF 安全张量容器，不执行代码，**官方推荐** |
| `.bin` / `.pth` | 旧式裸权重/检查点 |
| `.onnx` | ONNX 部署格式 |

> 区别：`.gguf` 是"文件格式"，`Q4_K_M`/`IQ3_M` 是"量化方案"；一个命名会同时出现**方案+文件拓展名**，因为 GGUF 文件把两者都写进名字。

## 十二、看命名速查结论

1. **数字 + B**：总参数；**A开头数字**：MoE 激活参数。
2. **没有 A**：稠密模型。
3. **K 档、IQ 档**：GGUF 量化；**bpw**：EXL2；**NF4/FP4/Int8**：bitsandbytes；**GPTQ/AWQ**：校准量化。
4. **Uncensored/Abliterated/Slerp/HauhauCS/NSFW 这类**：社区去审查与合并配方，与官方无关、质量参差。
5. **`.gguf` 是容器文件**，量化方案写在点号前。
